# 왜 RAG인가? 수업 도입용 데모

LLM에게 같은 질문을 두 번 던지는 아주 작은 웹 앱입니다. 한 번은 모델 혼자 답하게 하고, 한 번은 카페 정보를 프롬프트에 붙여 넣고 답하게 합니다. 청킹, 임베딩, 벡터 DB를 배우기 전에 RAG의 핵심 아이디어를 먼저 보여 줍니다.


## 실행 방법

```bash
pip install -r requirements.txt
cp .env.example .env      # 그다음 .env 파일에 API 키를 넣으세요
python app.py
```

브라우저에서 http://127.0.0.1:5000 을 여세요.

`.env.example`에는 수업용 aiclab 서버(채팅 qwen3-14b, 임베딩 bge-m3, 리랭커 bge-reranker-v2-m3)가 들어 있고 키 하나로 셋 다 씁니다. 채팅은 OpenAI 호환 API라면 어떤 것이든 동작합니다(Groq, xAI 등 예시는 `.env.example` 아래쪽). 의미 검색과 리랭커는 `EMBED_BASE_URL`, `RERANK_BASE_URL`이 있을 때만 켜집니다.

## 수업에서 데모 진행 순서

1. **모델 혼자.** "금요일에 텀블러 할인되나요?"를 *모델에게만 질문*으로 물어봅니다. 모델은 빈 브릿지 카페의 규칙을 본 적이 없으므로 추측하거나 모른다고 답합니다. 학생들에게 물어보세요. 이 답이 맞나요? 어떻게 확인할 수 있을까요?
2. **모델 + 카페 정보.** 같은 질문을 *카페 정보와 함께 질문*으로 물어봅니다. 이제 정확하게 답합니다(할인은 화요일에만). *전송된 프롬프트 보기*를 열어서 모델은 전혀 바뀌지 않았다는 점을 짚어 주세요. 우리는 올바른 텍스트를 프롬프트에 붙여 넣었을 뿐입니다. 이것이 RAG이고, 남은 수업은 이 단계를 자동화하는 방법을 다룹니다.
3. **파일에 없는 내용.** "무료 와이파이 있나요?"를 물어봅니다. 근거 기반 답변이라면 정보에 해당 내용이 없다고 말해야 합니다.
4. **실시간 수정.** 영수증의 규칙을 바꾸고(예: 텀블러 할인을 금요일 1,000원으로) 다시 질문합니다. 답은 모델의 기억이 아니라 텍스트를 따라갑니다.
5. **시스템의 파일을 바꾸기.** 브라우저가 아니라 에디터(VS Code 등)에서 `cafe_info.txt`를 직접 고치고 저장합니다. 2초 안에 화면의 영수증이 자동으로 갱신됩니다. 다시 질문하면 답이 바뀐 파일을 따라갑니다. 반대로 화면에서 고친 내용은 *파일에 저장*을 누르면 디스크에 기록되고, 에디터에서 바뀐 파일을 볼 수 있습니다. 핵심 메시지: 모델이 아는 것은 우리가 시스템에 넣어 둔 데이터가 전부이고, 데이터를 바꾸면 답도 바뀝니다.
6. **연결 질문.** "이 파일은 다섯 줄입니다. 카페 체인에 300쪽짜리 매뉴얼이 있다면 어떻게 할까요?" 여기서 청킹과 검색으로 넘어갑니다. 실제로 보여 주려면 긴 버전으로 바꿔 봅니다.

   ```bash
   cp cafe_info.txt cafe_info_short.txt     # 짧은 버전 보관
   cp cafe_info_long.txt cafe_info.txt      # 150줄짜리 운영 매뉴얼로 교체
   ```

   또는 `app.py`의 `INFO_FILE` 한 줄을 `cafe_info_long.txt`로 바꾸고 서버를 다시 실행해도 됩니다. 화면의 영수증이 자동으로 길어집니다. *전송된 프롬프트 보기*를 열어 질문 하나에 매뉴얼 전체가 통째로 들어가는 것을 보여 주세요. "2층 대관 비용은?" 같은 질문은 잘 답하지만, 프롬프트가 매번 이만큼 길어지는 것이 비용과 한계의 출발점입니다. 그래서 필요한 부분만 찾아 넣는 검색(retrieval)이 필요합니다.

## 내 PDF와 대화하기 (/pdf): 통째로 붙이기 → 청킹 → 검색 → 리랭커 → 도구

카페 데모 다음 단계입니다. http://127.0.0.1:5000/pdf 를 열거나 카페 데모 화면 위의 *내 PDF 올려서 대화해 보기* 링크를 누르세요. 화면의 다섯 가지 방식을 질문마다 바꿔 가며 비교합니다.

1. **올리기.** PDF를 끌어다 놓으면 `pypdf`로 글자를 뽑고 문단 단위로 잘라 왼쪽에 청크 목록을 보여 줍니다. 연습용 PDF가 두 개 들어 있습니다. `sample_cafe_manual.pdf`(4쪽, 청크 11개)는 짧아서 ①로도 충분하고, `cafe_manual_20p.pdf`(20쪽, 23개 장, 청크 52개)는 레시피·오픈/마감 절차·장비 고장 대응·직원 교육·FAQ까지 담은 긴 매뉴얼이라 검색 모드 비교용입니다. 학생은 자기 강의 자료나 논문을 올리면 됩니다. 스캔 이미지 PDF는 글자가 없어서 거절됩니다.
2. **① 전체 붙여 넣기.** 카페 데모와 똑같이 문서 전체를 system 프롬프트에 넣습니다. 짧은 문서는 잘 됩니다. 50쪽짜리 매뉴얼을 올리면 경고가 뜨고, 뒷부분을 물으면 모델은 모릅니다. qwen3-14b의 문맥은 32k 토큰이라 한국어 약 4만 자가 상한이고, 넘기면 API가 거절하는데 그 오류도 화면에 "프롬프트가 너무 커서 거절됨"으로 풀어서 보여 줍니다. 여기서 "그래서 다 붙여 넣을 수는 없다"로 넘어갑니다.
3. **② 키워드 검색 (TF-IDF).** 청크 중 질문과 글자 조각이 많이 겹치는 3개만 골라 보냅니다. 뽑힌 청크가 왼쪽에 노란색으로 표시되고, 답변 아래에 청크 번호와 점수, 프롬프트 길이가 나옵니다. `scikit-learn`만 있으면 로컬에서 돌고 API 키가 필요 없습니다. 한국어는 조사 때문에 단어 대신 글자 2~3개짜리 조각(n-gram)으로 셉니다. 종이 연습(문장 다섯 개와 질문을 주고 가장 가까운 것을 손으로 고르기)을 먼저 하고 이 모드를 보여 주면 "마법이 아니다"가 전달됩니다.
4. **③ 의미 검색 (임베딩).** 같은 구조에서 `retrieve_embedding()` 하나만 바뀝니다. 글자를 세는 대신 임베딩 서버(bge-m3)가 문장의 뜻을 1,024차원 벡터로 바꿔 주고, 코사인 유사도로 비교합니다. `app.py`에서 `retrieve_keyword()`와 `retrieve_embedding()`을 나란히 보여 주세요. 입력과 출력이 같고 "비교할 벡터를 누가 만드느냐"만 다릅니다. "강아지 데려가도 돼요?"처럼 문서의 표현(반려동물)과 단어가 다른 질문으로 둘을 비교해 보세요.
5. **④ 검색 + 리랭커.** 임베딩으로 후보 10개를 빨리 추린 뒤, 리랭커(bge-reranker-v2-m3)가 질문과 후보를 한 쌍씩 정독해서 다시 순위를 매깁니다. 점수가 0~1 확률처럼 나오므로 "관련 있음/없음"이 훨씬 또렷하게 갈립니다. 임베딩은 빠르지만 대략적, 리랭커는 느리지만 정확해서 실무 RAG는 보통 둘을 이어 씁니다. `retrieve_rerank()`.
6. **⑤ 에이전트 (도구 호출).** `retrieve()`를 `search_documents(query)` 도구로 감싸고 모델이 언제 검색할지 스스로 정합니다. 답변 아래에 모델이 만든 검색어와 돌려받은 청크가 표시되고, *전송된 프롬프트 보기*에 도구 호출과 결과가 그대로 나옵니다. 1주차 계산기 에이전트와 구조가 같습니다. 도구가 숫자 대신 글자를 돌려줄 뿐입니다. "이 문서를 요약해 줘"처럼 검색어를 정하기 애매한 질문을 던지면 모델이 어떻게 검색하는지 보는 것도 재미있습니다.

`app.py`에서 학생이 읽을 함수는 순서대로 `chunk_pages()`, `retrieve_keyword()`, `retrieve_embedding()`, `retrieve_rerank()`, `build_chat_messages()`, `run_agent()`입니다. 설정은 `.env`의 `CHUNK_SIZE`, `TOP_K`, `MAX_PDF_CHARS`, `RERANK_CANDIDATES`로 바꿉니다. Qwen3는 답 앞에 긴 '생각' 과정을 쓰는데 `DISABLE_THINKING=1`로 끕니다(혹시 남으면 `strip_think()`가 떼어 냅니다). 올린 문서는 서버 메모리에만 있고 서버를 재시작하면 사라집니다.

## 파일 구성

| 파일 | 역할 |
|---|---|
| `app.py` | Flask 서버. 학생이 꼭 읽어야 할 함수는 `build_messages()` 하나입니다. 일반 프롬프트와 증강된 프롬프트의 차이를 보여 줍니다. |
| `/info` (app.py) | 디스크의 `cafe_info.txt`를 읽고(GET) 쓰는(POST) 작은 API. 화면이 2초마다 파일 수정 시각을 확인해 바뀌면 자동으로 다시 불러옵니다. |
| `templates/index.html` | 카페 데모 화면. |
| `/pdf`, `/pdf/upload`, `/pdf/chat` (app.py) | PDF 채팅. 청킹 `chunk_pages()` → 검색 `retrieve_keyword()` / `retrieve_embedding()` / `retrieve_rerank()` → 증강 `build_chat_messages()` → 도구 `run_agent()`. |
| `templates/pdf.html` | PDF 채팅 화면. 업로드, 청크 목록(검색된 청크 강조), 다섯 가지 방식 선택, 대화 스레드, 전송된 프롬프트. |
| `sample_cafe_manual.pdf` | PDF 채팅 연습용 문서(4쪽). `cafe_info_long.txt`를 PDF로 만든 것. |
| `cafe_manual_20p.pdf` | 20쪽짜리 긴 운영 매뉴얼(가상). 긴 문서에서 검색이 왜 필요한지 보여 주는 용도. |
| `make_cafe_manual.py` | 위 20쪽 매뉴얼을 만드는 스크립트. 내용을 고친 뒤 Chrome 헤드리스로 PDF 출력. |
| `cafe_info.txt` | 카페의 비공개 정보(지어낸 내용이라 어떤 모델도 알 수 없습니다). 디스크의 이 파일이 기준 데이터입니다. |
| `cafe_info_long.txt` | 같은 카페의 150줄짜리 운영 매뉴얼. 영업시간, 메뉴, 알레르기, 할인, 멤버십, 대관 등 12개 섹션. 원래 다섯 가지 규칙은 그대로 들어 있고 와이파이는 일부러 뺐습니다. |
